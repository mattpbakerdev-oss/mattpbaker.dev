Listing Check: a pre-publish checker for Bangkok rental agents

Next.js · Supabase · Postgres · Claude Sonnet via edge function · Claude Code

An agent pastes a draft listing. The tool scores completeness out of 100 with per-field fixes, benchmarks the rent per square metre against comparable listings in the same building, tier and area, and offers an AI rewrite in English and Thai that may only use facts from the draft. The agent accepts each part or edits it; nothing is applied without a click. Built in four evenings from a one-page spec, with the build log kept from the first commit.

Try it live ↗ Source on GitHub ↗ Build log ↗ Spec ↗

What the AI got wrong

Two things, and the second mattered more. The rewrite model turned a draft that said "furnished" into "fully furnished": a small, plausible upgrade that would start an argument on move-in day. Then my own fact checker, built to catch exactly that, was wrong first: it flagged "looks out over the pool" as an invented claim when the draft said "pool view". Four of its first five flags were false.

How I fixed it

The checker was fixed before the model was blamed: a view of something now implies the thing exists, with tests for both cases. The genuine catch stayed caught. I then ran the same 20 listings through Opus and Sonnet and compared added facts, time and cost: Sonnet was as clean, a third faster and a third of the price, so it's the default. Every rewrite is logged with its added-facts list.

Spec mistakes the build caught

The spec I wrote had a threshold that contradicted itself, a building count that was wrong, a SQL round() that wouldn't compile, and a metric target I'd guessed without looking at the data. The log records each one, who caught it, and the fix. My first benchmark rule was also worse than the agent's alternative when measured, so the measured one shipped.

Decisions I'd defend

Sample data generated from public market medians rather than scraping anyone's listings, with every anchor sourced. A map preview considered and rejected in favour of a building card that tells the agent what the benchmark is comparing against. Rate limiting and a hashed IP before the URL went public. A marketing checklist reviewed and mostly skipped, because this is an internal tool.

Up Lock: exercise to unlock your apps

Swift · SwiftUI · Vision pose detection · Family Controls · RevenueCat · Claude Code

An iPhone app that blocks distracting apps until you do a set of push-ups, squats or jumping jacks. The camera counts reps on the phone itself, and a finished set unlocks the app for a timed window. Daily limits, streaks, stats and a subscription. Built from ten dated design specs and eighteen implementation plans; about 145 tests.

Live on the App Store ↗

What the AI got wrong

Apple's pose model gives you joints, not exercises. It has no idea what a push-up is, so the first version counted anything that bent an elbow, including standing in front of the phone and waving. My first anti-cheat rule then overcorrected: it required the hips to be visible to prove you were horizontal, and real push-ups stopped counting because your legs are out of frame when the phone is on the floor.

How I fixed it

A rep is now defined in terms the model understands: elbow angle mapped to a 0 to 1 signal, which has to drop below 0.35 and rise above 0.70, with a dead band in between so jitter can't flip it and a half-second floor so a twitch can't double count. Standing is rejected only when a visible cue positively shows it (torso near vertical, or nose well above the shoulders), never because a joint is missing. Each rule has a test: pushupStandingFakeIsRejected, pushupArmsOnlyNoHipsCountsTheRep, deadBandJitterDoesNotCount.

Rep counting runs on the phone and nothing is uploaded. Marketed with four TikTok posts a day, it passed 10,000 views in its first week.

UGC shorts pipeline: talking-head takes in, finished videos out

TypeScript · Remotion · whisper.cpp · ffmpeg · Claude Code

I'm paid to make short videos promoting a social media scheduler. Editing each one by hand didn't scale, so I built a pipeline: you write a small storyboard per video ("when I say this phrase, show this number, play this sound") and everything else is automatic: silence trimmed, colour corrected, captioned from Whisper word timings, titles and graphics placed around the face. The first version was Python and ffmpeg in September; the October rebuild on Remotion has a storyboard language, a validator that fails the build naming the missing phrase, a retake detector, and 21 test files. 72 commits in a week, starting with a design spec and an implementation plan.

Source on GitHub ↗ Output: Short ↗ Output: Short ↗ Output: TikTok ↗

What the AI got wrong

Whisper is confidently wrong about time. It stretches a word across silence, so on joined audio a take's first word started inside the previous take. It hallucinates words in trailing silence. It mis-times words that sit tight against a cut. And on the first batch, the agent cut the videos from my script rather than from what I actually said, and merged "barber shops" into one word so a cue never fired.

How I fixed it

Each take is transcribed separately and offset onto the joined timeline. Words placed after the measured end of speech are dropped as hallucinations. Word times are mapped through the cuts after transcription, not before. Cuts come from the transcript, never the script. Cue words were changed to ones Whisper doesn't merge, and a caption-fixes table handles the brand names it mangles. Each failure became a rule with a test.

27 videos live across TikTok, Reels, Shorts and Facebook in the first three weeks, about 26,000 views, every one tagged by hook so I know which to make more of.
Your four responsibilities

I already work in your loop

Discovery, spec, build, measure. Listing Check did all four in one project, in your domain. The others show the same habit at smaller scale.

1 · Discovery & validation

Pick a real problem, check the data

Listing Check started with the question "what does an agent get wrong fifty times a day?", not with a feature. Two years on a shop floor asking people what they need before selling them anything. I call small business owners myself. The florist lead-list mistake (below) is why I check ground truth before building.

2 · Specification

One page, then build

Listing Check, Up Lock and the video pipeline each began with a written spec and plan before any code: user, scope, rules, metric, what's out. The specs had mistakes; the logs show them being caught. A spec that's never wrong hasn't been tested.

3 · Build with agents

Direct, review, decide

I assign the agent work, read every plan before it builds, and don't accept code I can't explain. When it reached for Docker or a map I said no and wrote down why. When it caught my mistakes, that went in the log too. I keep humans in the loop where mistakes are expensive: nothing from the AI rewrite is applied without a click.

4 · Measure & iterate

Numbers decide

The benchmark rule was tested three ways and my intuition lost. The price verdict bands were softened after measuring that one in three fair prices got questioned. The rewrite model was chosen on a 20-listing comparison. The headline metric was measured, not claimed: 71 flagged listings, 79.6 to 98.0.
